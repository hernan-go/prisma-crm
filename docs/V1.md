# PRISMA CRM V1 — operación y cierre

## Instalar y revisar localmente

Requiere Node 24 LTS (también compatible con 22.12+), npm y MySQL 8.0.16+; validado con MySQL 8.4.8. Mantiene React/Express/mysql2 y la arquitectura del proyecto existente.

Desde la raíz del repositorio:

```powershell
npm ci
# Copiar .env.example a .env SOLO en una instalación nueva.
# En este equipo .env ya existe: conservar sus credenciales MySQL locales.
npm run db:migrate
npm run db:seed
npm run auth:configure
npm run dev
```

Para Vite usar APP_URL=http://localhost:5173. Para revisar el build usar APP_URL=http://localhost:3001, ejecutar `npm run build` y `npm start`. El backend sirve frontend y API. El proceso temporal 3002 y prisma_test son exclusivamente QA.

## Autenticación

`npm run auth:configure` solicita y confirma la contraseña en una terminal interactiva sin mostrarla. Genera hash **scrypt N=131072, r=8, p=1**, sal aleatoria de 16 bytes y secreto aleatorio de 48 bytes. Guarda únicamente ADMIN_PASSWORD_HASH y SESSION_SECRET en `.env`, conservando las demás variables. La contraseña plaintext no se almacena.

Para el hosting: `npm run auth:configure -- --export` guarda las variables en `private/auth.env` con creación exclusiva (no sobrescribe un archivo existente). Copiar sus valores al panel privado. No enviarlos por chat, subirlos a Git ni registrarlos en logs. El comando no imprime secretos. La contraseña definitiva debe elegirla Hernán, fuera de las pruebas.

Sesiones de 8 horas en MySQL: token aleatorio en cookie, identificador HMAC en DB, HttpOnly, SameSite=Strict, Secure y prefijo `__Host-` en producción. Logout borra la sesión en servidor. Rotar el hash o SESSION_SECRET invalida las anteriores. No hay usuarios, roles, registro ni recuperación automática: para rotar, repetir el comando y reiniciar. Login limitado por IP y globalmente; los contadores de rate limit son locales al proceso (una instancia V1). Todas las rutas administrativas requieren sesión, incluidas `/api/health` e importación. Login/session/logout son las únicas rutas públicas de autenticación. Origen y Fetch Metadata se validan en escrituras.

No se mantiene el antiguo bypass basado en EXTERNAL_PROTECTION_CONFIRMED. Si esa variable sigue en un `.env` antiguo, no concede acceso y puede retirarse. Sin hash/secreto válidos el acceso queda cerrado.

## Agenda y modalidad

- Solapamiento: mismo día, inicio nuevo < fin existente y fin nuevo > inicio existente. Los bloques consecutivos están permitidos.
- Una persona no puede solapar actividades, aunque los docentes sean distintos.
- Un docente no puede solapar actividades distintas.
- Grupal admite múltiples asistentes en el mismo bloque completo. Bloques parcialmente superpuestos del mismo taller deben unificarse o separarse.
- Individual admite un asistente. Informática se migra/crea como individual; lunes a sábado. El resto conserva modalidad grupal por defecto.
- Las reglas se comprueban en frontend y, de manera definitiva, en backend al crear, editar e importar. Escrituras de inscripciones, períodos, cuentas, pagos e importaciones se serializan con el bloqueo MySQL compartido para evitar dobles reservas simultáneas.
- Cambiar docente o modalidad de una actividad se rechaza si introduce conflictos en sus inscripciones existentes. Las asignaciones siguen siendo actuales, no versionadas históricamente.

## Períodos

Crear propone el primer mes libre a partir del mes siguiente al actual. Año y mes independientes, períodos existentes identificados y errores limpiados al cambiar valores. Meses anteriores y futuros lejanos muestran avisos sin bloquearse (rango técnico 2020–2100).

Configuración permite editar/eliminar solo períodos sin inscripciones, cuentas ni publicidad asociada por fecha. Las cuentas con importe indefinido también cuentan como datos. Un período con datos únicamente se cierra/reabre. Cerrar conserva todo y bloquea escrituras de inscripciones, cuentas, pagos y publicidad; mover un movimiento desde un período cerrado también se rechaza. Personas y configuración general se mantienen independientes del cierre.

## Importación de Google Forms

Personas → Importar → Importar inscripciones desde Google Forms PRISMA. Seleccionar período abierto y CSV UTF-8. No utilizar el CSV real hasta terminar la validación local.

1. Leer: detecta encabezados conocidos, sin escribir en DB. Mantiene original y propuestas.
2. Corregir columnas manualmente y aplicar mapeo si cambiaron encabezados. Aplicar reinicia aprobaciones.
3. Revisar una respuesta por vez con filtros Todas/Pendientes/Revisadas/Errores/Duplicados/Omitidas y navegación Anterior/Siguiente.
4. Editar nombre y apellido sugeridos; nunca se aprueban automáticamente nombres compuestos. Corregir teléfono, DNI, email, dirección y observaciones.
5. Coincidencias fuertes: teléfono normalizado, DNI sin separadores y email. Crear sin coincidencias, conservar la persona y agregar inscripciones, actualizarla o descartar la respuesta. Actualizar reemplaza campos básicos, incluso vacíos; preserva emergencia y estado. Personas archivadas deben reactivarse explícitamente antes de agregar inscripciones.
6. Revisar docente, actividad, día y horas. El docente debe ser el de la actividad configurada; no se cambia la configuración de todo un taller desde una respuesta. Turnos mañana/tarde se combinan. Se permiten varias actividades y días. Inscripciones existentes conservan slots anteriores y agregan los nuevos sin repetir slots exactos.
7. Opciones desconocidas quedan sin resolver: corregir manualmente o desmarcar “Incluir esta inscripción”. No se inventan duraciones. La excepción explícita es Gimnasia y Fortalecimiento Corporal, viernes 13:30 → 14:30. “Programa acompañamiento cognitivo” es un alias explícito de Acompañamiento Cognitivo.
8. Pago: texto original y monto/medio/fecha editables. T=transferencia/Cartera Hernán, E=efectivo/Cartera Jesica. La cartera se corrige eligiendo el medio correspondiente; no puede separarse arbitrariamente del medio. Pago desmarcado por defecto. Para incluirlo se exige además aprobar monto/medio/fecha. Si falta fecha, queda vacía; si falta año se propone el del período, siempre sujeto a revisión.
9. Aprobar individualmente cada respuesta seleccionada. Editar la respuesta reinicia su aprobación. El botón final permanece bloqueado ante pendientes o errores conocidos.
10. Confirmar lote: una transacción guarda personas, inscripciones/cuentas y pagos. Cualquier conflicto revierte el lote. Cada confirmación tiene identificador y recibo persistente; reintentar la misma no duplica movimientos. Otra importación con un pago idéntico se rechaza y requiere excluirlo tras revisión.

Límites: archivo 5 MB, 10.000 filas/100 columnas en lectura; commit específico Forms máximo 1.000 respuestas por lote. Para volúmenes mayores dividir el CSV. No resuelve nombres semánticamente ni opciones nuevas mediante IA. Los originales no se suben a terceros; se procesan por el servidor del CRM.

El importador genérico XLSX/CSV sigue disponible con mapeo y revisión individual. Solo importa personas. Mantiene creación forzada explícita para duplicados intencionales; Forms no crea duplicados intencionales silenciosamente. La migración histórica del Excel requiere conciliación humana y no está automatizada.

## Limpieza QA: nunca automática

Preferir una base productiva nueva: migraciones + seed crean configuración, sin personas ni períodos. No copiar prisma_dev/prisma_test al hosting.

Si se necesita limpiar una base existente, primero respaldarla y pausar escrituras. `npm run qa:cleanup` **solo genera** `private/qa-cleanup-plan.json`. No sobrescribe un plan existente. El plan enumera IDs, valores actuales y relaciones (pagos, cuentas, inscripciones, slots); todos comienzan con reviewed=false.

Revisar cada candidato y sus relaciones. Marcar reviewed=true exclusivamente en registros comprobados como ficticios. Dejar el resto en false. Los nombres conocidos incluyen QA Ficticia Noviembre, Importada CSV/XLSX Ficticia, Marta Ficticia/Prueba y Juan Test, y la actividad/docente explícitos de QA. La publicidad se propone por etiquetas ficticias/QA y requiere la misma revisión humana. Una etiqueta no prueba por sí sola que el registro sea descartable.

Solo después de revisión y backup, ejecutar manualmente:

```powershell
npm run qa:cleanup -- --apply --database prisma_dev --backup-confirmed
```

Usar el nombre real de la base revisada. La herramienta exige coincidencia con la conexión y una huella íntegra de registros/relaciones; si algo cambió desde el plan, aborta. Borra relaciones únicamente de personas aprobadas. No elimina una actividad/docente si quedan relaciones no incluidas. No borra períodos, configuración real ni registros fuera de la lista permitida. Toda la limpieza es una transacción. Regenerar un plan requiere archivar/mover manualmente el anterior dentro del directorio privado. No subir estos planes ni backups a Git.

## PWA, UX y alcance mobile

SVG maestro en public/branding/logo_prisma.svg, idéntico al oficial. Favicon SVG y PNG 192/512 derivados, sin deformar ni recolorear. Los iconos son `purpose:any`; no se declara maskable para evitar recortar el logo vertical.

Manifest standalone, nombre PRISMA CRM. Puede agregarse a pantalla de inicio desde navegadores compatibles con HTTPS (localhost sirve para QA). Online-only: service worker no almacena recursos, API ni personas; sin conexión muestra aviso y reintento. No hay edición offline, sync ni base local. La instalación depende del navegador/sistema.

Modales centrados con scroll interno y acciones fijas dentro del cuadro. Escape/cancelar solicitan descartar cambios si se editó el formulario. Activa/Archivada mantienen texto y color. Finanzas usa ámbar apagado; actividades mantienen teal.

POST-V1: barra inferior mobile, hamburguesa avanzada, bottom sheets y navegación más similar a app; no se implementaron en esta iteración. También quedan futuras auditorías de autores y versionado de asignaciones docentes.

## Validación y release

```powershell
npm run lint
npm run typecheck
$env:RUN_DB_TESTS='true'
$env:DB_NAME='prisma_test'
npm test
Remove-Item Env:RUN_DB_TESTS
Remove-Item Env:DB_NAME
npm run build
npm audit
```

La suite real limpia únicamente las tablas de la base prisma_test, cuyo nombre valida. No ejecutar contra bases con datos reales. Retirar las variables de prueba antes de iniciar el entorno habitual.

Migraciones 001 esquema base; 002 modalidad group/individual (Informática individual); 003 recibos de importación; 004 sesiones. El runner aplica en orden y registra schema_migrations con bloqueo exclusivo. Reejecuciones normales no repiten DDL ni pierden datos. MySQL hace commit implícito del ALTER de 002: ante una interrupción excepcional entre DDL y registro, revisar el esquema antes de reintentar; no borrar registros de schema_migrations ni resetear bases para resolverlo. Las seeds no sobrescriben reglas de días personalizadas.

Ver README para parámetros SiteGround. Este cierre no autoriza desplegar, cargar datos reales ni vincular cuentas de hosting.
